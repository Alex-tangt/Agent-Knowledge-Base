# 需求 1 的形状：跨应用 / 跨设备的个人记忆基座（规格草案）

状态：**草案**（2026-10-09）· **不是 ADR** —— 两个决定仍开放：**权威点住哪**、**引擎谁写**。
范围：**只需求 1**。需求 2（沉淀 / 简报 / 偏好画像 / 闸门 / 行为改变度量）**明确出界**，见 §10。

> **这份文档是双用的**：① 我们的施工图；② 候选框架的**体检表**（§8 给逐条问法）。
> 因此它**刻意与引擎无关**——不写"用 Qdrant / 用 Postgres"，只写"要什么形状"。

前置决议（本仓库对话已定）：**主体 = 人**（记忆不隶属任何 agent）；**不要求离线**；**以数据库为核心构建**。

---

## 1. 四条不变量（违反其中任一条，需求 1 不成立）

| # | 不变量 | 为什么是硬约束 |
|---|---|---|
| **I1** | **原文是一等对象**：存进去的正文**逐字保留**、可按单元读回；任何抽取 / 摘要 / 沉淀都是**另存的派生**，**绝不覆盖原文** | 否则"范围筛选"和"后续沉淀"都建立在被改写过的原料上 |
| **I2** | **记忆按「人」分，不按 agent 软件分** | "换一个 agent 就能用、不用重新培养"的**唯一**实现方式；按 agent 分就是每换一个就重来 |
| **I3** | **所有写入路径过同一份元数据契约** | 只要有一条路径能绕过契约，"按元数据筛"就会漏，而且**漏得无声** |
| **I4** | **不可用即显式报错**，绝不静默返回空结果 | 对 agent 而言"查不到"与"没有记忆"是两回事；静默返空会让它把"我没告诉你"当成事实 |

---

## 2. 主体模型（需求 1 只需要**一个**落点）

- **存储键 = 人**（一个 person 一份记忆）。
- **agent 只是凭证**：每个 agent 软件一个身份 / 令牌，**归属到同一个 person**。
- 需求 1 **不需要**"谁能写关于我 / 审阅面 / 撤回"这三个落点——它们属于需求 2。

---

## 3. DB schema

### 3.1 `entries`（核心表：一行 = 一个条目）

| 字段 | 类型 | 必填 | 来源 | 说明 |
|---|---|---|---|---|
| `id` | text (PK) | ✅ | 派生 | 稳定标识；沿用现有约定（`<domain>/<slug>`，只读语料 `repo:<label>/<rel>`） |
| `person_id` | text | ✅ | 接入身份 | **I2 的落点**。所有查询默认按它收窄 |
| `title` | text | ✅ | 写入方 | |
| `body` | text | ✅ | 写入方 | **I1 的落点**：原文 / 摘要正文，逐字保留 |
| `kind` | text | ✅ | 写入方 | **来源形态**：`article` / `video` / `note` / `doc` / `chat`（新增轴） |
| `type` | text | ✅ | 写入方 | **知识角色**：沿用现有 `VALID_TYPES` = `project-knowledge` / `topic` / `decision` / `research` |
| `source` | text | ✅ | 写入方 | 主出处：URL / 仓库路径 / label（沿用） |
| `sources` | json | 可选 | 写入方 | 多出处数组（沿用现有 frontmatter） |
| `tags` | text[] | ✅（可空数组） | 写入方 | 受控词表（沿用 `tags.md`） |
| `status` | text | ✅ | 写入方 | `current` / `draft` / `superseded` / `archived`（沿用） |
| `event_time` | timestamptz | 可选（见 §4） | 写入方 | **我看到 / 接触它的时间** ← "今天看的"依据（新增） |
| `content_time` | timestamptz | 可选 | 写入方 | 内容自身的发布时间（新增） |
| `created_at` | timestamptz | ✅ | 系统 | 落库时间 |
| `updated_at` | timestamptz | ✅ | 系统 | 最后修改时间 |
| `owner` | text | 可选 | 收录配置 | 域所有者（沿用） |
| `writable` | bool | ✅ | 收录配置 | 可写域 / 只读语料（沿用） |
| `classification` | text | ✅ 默认 `private` | 写入方 | `private` / `internal` / `public`（沿用） |
| `residency` | text | ✅ 默认 `local` | 写入方 | `local` / `cloud`（沿用） |
| `tenant` | text | 可选 | 接入身份 | 隔离边界（沿用） |
| `deleted_at` | timestamptz | 可选 | 系统 | **软删除**；永不物理删除 |
| `supersedes` / `superseded_by` | text | 可选 | 写入方 | 取代链（沿用） |
| `archive_reason` | text | 可选 | 写入方 | 归档原因（沿用） |

**索引**（需求 1 的最小集）：
- `(person_id, deleted_at)` —— 所有查询的默认前缀
- `(person_id, event_time)` —— **范围筛选**（"今天 / 本周"）
- `(person_id, kind, event_time)` —— "今天看的视频"
- `(person_id, status)` —— 取新弃旧
- `tags` 的 GIN（或等价）—— 标签筛
- 全文索引（`body` + `title`）—— 词法召回
- 向量列（`body` 的嵌入）—— 语义召回

### 3.2 `sources`（来源注册表：决定基表 extent）

| 字段 | 说明 |
|---|---|
| `label` / `path` / `owner` / `enabled` | 沿用现有注册表语义；相对路径按仓库根解析 |
| `included` / `excluded` | 显式 overlay（include/exclude 路径模式） |

**收录是 DDL，不是写数据**：注册表默认 ∪ 显式 overlay。**来源不可达 ≠ 条目消失**（见 §6-E）。

### 3.3 预留字段（**需求 2 才启用，现在不建索引、不强制**）

`evidence_ids`（证据回指）/ `derived`（是否生成物）/ `input_fingerprint`（生成物的输入指纹）。

> 取舍说明：DB **加列便宜、改列贵**，所以预留；但按仓库"实例数为 0 的机制只写触发条件"的规矩，
> **现在不建索引、不写实现、不进任何查询路径**。

## 4. 元数据契约

| 规则 | 内容 |
|---|---|
| **必填** | `id` `person_id` `title` `body` `kind` `type` `source` `tags` `status` `writable` `classification` `residency` |
| **值域受约束** | `kind` ∈ {article, video, note, doc, chat}；`type` ∈ `VALID_TYPES`；`status` ∈ {current, draft, superseded, archived}；`classification` / `residency` 沿用 |
| **`event_time` 何时必填** | **`kind ∈ {article, video, chat}` 时必填**——因为这一类条目**存在的意义就是"我什么时候看的"**；漏了就永远补不回来 |
| **`tags` 从受控词表取** | 沿用 `tags.md`；新标签先入表再用 |
| **校验失败的行为** | **拒绝写入 + 显式报错**（不半写、不落库）；与既有写入网关的"校验前置、HEAD 不动"一致 |
| **两条写入路径都要过** | ① 工具写（MCP `add` / `supersede`）② 外部/同步落文件后入库。**I3 的落点**——两条路径共用同一个校验器与同一份 schema |

## 5. 查询面（筛选接口，需求 1 的最小集）

| 参数 | 语义 |
|---|---|
| `person_id` | 隐式（由接入身份决定），**不可由调用方指定** |
| `time_range` | 对 `event_time` 的开闭区间（"今天 / 本周 / 某天"） |
| `kind` | 来源形态多选（"文章 + 视频"） |
| `tags` | 标签（任一 / 全部） |
| `status` | 默认取新弃旧（`current` + 无 status） |
| `writable_only` | 沿用 |
| `query` | 词法 + 语义召回 |

**分级**：纯元数据筛（快，可只走索引）↔ 带 `query` 的检索（走召回 + 融合）。
**"筛出今天看的文章"应当只走元数据筛**——这是 §8 里要问候选框架的第一件事。

## 6. 需求 1 完成判据（**A–G，每条都能跑**）

| # | 判据 | 怎么验 |
|---|---|---|
| **A** | 换一个 agent 软件接入，**读到同一份**，无迁移动作 | 第二消费者装好后直接查同一个条目 |
| **B** | 第二台设备能读能写，且写入的**在第一台可见** | 两台设备各写一条，互查 |
| **C** | 可见延迟符合预期（惰性追平即可，**不需手动同步**） | 记录"写完 → 另一台可见"的延迟 |
| **D** | 记忆不可用时**显式报错**，不静默返回空 | 停掉权威点后再查，断言得到错误而非空集 |
| **E** | 来源不可达 / 被移除时**不误删** | 把某个来源根改到不存在的路径 → 断言条目仍在、只报 `deferred_removed` |
| **F** | 两条写入路径**都满足元数据契约** | 各造一条违规写入 → 断言都被拒 |
| **G** | 存在备份 / 快照，且**证明得出可恢复** | 删掉权威点，从快照恢复后 A–F 仍通过 |

> **E 是已知缺陷**：现有实现里 `settings._readonly_items()` **只在 JSON 结构非法时**返回 `complete=False`，
> **从不检查来源根是否可达**；而 `index.py:210` 的 docstring 承诺了"来源根不可达 → 不删条目"。
> 跨设备（同步目录离线）与跨项目（仓库改名 / 换盘）**都在这条路径上**，所以它是需求 1 的前置修复。

## 7. 为需求 2 预留的 6 条拓展要求（**框架体检清单**）

这 6 条**不需要理解框架的合成层**，只看数据模型与 API：

| # | 要求 | 为什么它决定"能否拓展需求 2" |
|---|---|---|
| **X1** | 原始输入是**一等对象**（逐字保留、可单元读回） | 沉淀必须基于可靠原料（= I1） |
| **X2** | 元数据**可挂自定义字段且在查询时过滤**（不只是展示） | "圈定沉淀范围"完全依赖它 |
| **X3** | 写入**可脚本化且幂等**（批量读 / 写 / 重试不重复） | 巩固 pass 的基本要求 |
| **X4** | 可**自定义类型与关系**（沉淀物类型 + 证据回指到原始条目 id） | 防自我污染的前提 |
| **X5** | 可挂**后台任务且失败可见**（定时触发、失败可观测） | 反面教材：Basic Memory 那个"静默永不执行"的已发布特性 |
| **X6** | 数据落**标准存储、可外部直读** | 否则沉淀层要与框架内部语义搏斗 |

## 8. 用它做框架体检：逐条问什么

| 我们的要求 | 问候选框架 | 怎么验 |
|---|---|---|
| I1 / X1 | 存进去的正文**逐字**保留吗？能按单元读回吗？ | 读数据模型文档；**1 条样本**入库后直接查原文 |
| §5 `time_range` | 能否对**自定义时间字段**做范围过滤？还是只有它自己抽的时间？ | 同一条样本带上 `event_time`，按区间查 |
| I2 | 记忆能按**人**分（而非按 agent / 会话）吗？`bank` / `namespace` 的粒度可配吗？ | 读配置项（如 `dynamicBankGranularity`） |
| I3 | **两条写入路径**（工具 / 文件）能否共用同一份 schema 校验？ | 读写入 API；看是否有 schema enforcement |
| §4 值域 | 能约束字段值域吗（`kind` / `type` / `status` 的枚举）？ | 读 schema / DDL |
| X4 | 能自定义类型 + 存**指向其他条目的引用**吗？ | 读 schema；看是否只有它自己的 fact 类型 |
| X5 | 后台任务**失败可见**吗（有状态 / 告警 / partial 上报）？ | 读运维文档 |
| X6 | 能否用外部 SQL 直读数据？ | 看存储是不是标准表；或看导出格式 |
| §6 E | 来源不可达时**会不会删条目**？ | 文档 + 实测：把来源改到不存在的路径 |

> **判据**：X1 / I1 与 §5 `time_range` 是**门槛**——两条不过，说明该框架的主场是"会话经验"而非"文档/条目库"，
> 与需求 1 的形状不吻合，**不必再看合成层**。

## 9. 与现有系统的关系

- **`type` / `status` / `tags` / `owner` / `classification` / `residency` / `supersedes` 全部沿用**——
  现有 KB（约 40 条）与只读语料可**无损对应**。
- **新增**：`person_id` / `kind` / `event_time` / `content_time` / `created_at` / `updated_at` / `deleted_at`。
- **新增索引**：时间范围 + kind + status + tags + 全文 + 向量。
- 现有 `authoring.py` 的 `REQUIRED_KEYS` / `VALID_TYPES` 是这份契约的**前身**，可延伸而非推翻。

## 10. 明确出界（属需求 2，本规格不覆盖）

沉淀与合成（事实 / 偏好 / 结论）· 简报 / 画像 / 认知结构 · 定时巩固 pass · 缓存与失效策略 ·
自我模型与闸门 · 审阅面与撤回 · 行为改变度量 · 多跳检索的迭代策略。

**出界不等于 schema 不管**：§3.3 的预留字段与 §7 的 6 条要求，就是为将来接续留的接口。
