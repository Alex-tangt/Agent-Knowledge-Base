## 1. 需求与愿景

**场景 1**：移动端 AI 小应用，总结看过的视频/文章的碎片化知识，存进知识库。
**场景 2**：另一项目的开发信息要在简历/别处复用——**信息同步**问题。
**愿景**：一个个人的知识库，不局限于不同应用、不同机器，所有 personal agent 都可访问；不只静态检索，
还要能整理个人的知识与认知体系、总结偏好；**接入一个新 agent，不需要重新培养**。

**修正 1（2026-10-09）**：手机端**只是 agent 的前端**——但**后端不再跑在云服务器上，直接跑在这台电脑上**。
→ 手机是**多入口之一**；权威点 = 本机（见 D8）。

**修正 2（2026-10-09）**：**真相源不是"以数据库为核心"那么简单** —— 见 D3。

**场景 2 已有活实例（不是假设）**：`memory_agent/readonly_repos.json` 已把三个 repo 收成只读域
（绝对路径），而可写 KB 里**又有一套** `projects/<slug>/*.md` 手写摘要 —— **同一项目的两份表示，会漂移**。

### 1.1 为什么"文件系统范式"对我们有实质吸引力（用户理由 + 补充证据）

用户提出的理由（**我认为成立**）：

1. 文件系统**特别容易实现读写权限的分离**（某子树只读、某子树只有人能写）；
2. **工作区分离**天然（一个项目 / 一个来源一个子树）→ 整个记忆系统**井井有条**；
3. **coding agent 很熟悉文件操作**（read / ls / grep / mv），不需要学新协议。

**补充证据（我们自己的数据，支持第 3 条）**：**工具协议失配是真实失效来源**——
`#63` 的 `fallback` **26%（5/19）**、`#74` 的 `fallback` **13.0%（26/200）**。
即 agent 对**自定义工具面**的熟悉度**直接吃成功率**；而文件操作是模型最熟练的动作之一。
→ **"文件系统形态"不是审美，它有可测的收益。**

## 5. 调研结论

### 5.1 记忆框架 census（15 个系统）

见 [census](../experiments/memory-frameworks-survey/README.md)。关键三条：
两个阵营（文件真 / DB 真）· **共识 6 条**（派生层可重建、provenance 是入场券、MCP 是共享边界、scoping ID 强制、追加式写入、LLM 抽取原子单元）·
**"无人做的那一格"6 条**，其中最重要：**没有任何框架证明"记忆改变了行为"**（全场只发布 recall 类基准）。

### 5.2 三范式对比

| | **Hindsight**（学习） | **OpenWiki Brains**（文件系统） | **MemOS**（OS） | **OpenViking**（文件系统 / 火山引擎） |
|---|---|---|---|---|
| 原文逐字（**记忆接口上**） | ✅ chunks + `original_text` | ❌ raw 留盘但**接口不可达** | ⚠️ 仅非默认 Fast | ❌ memory 层 LLM 改写 |
| 写入零 LLM | ✅ 文档化 | ❌ | ⚠️ 未验证 | ❌ 强制模型 |
| 元数据可筛 | ⚠️ 未核 | ❌ 保留但**不能筛** | ✅ 强 | ⚠️ 自定义字段**静默丢弃** |
| 跨应用（个人） | ✅ MCP | ❌ 个人脑无路径 | ✅ | ✅ 最强 |
| 跨设备 | ✅ PG 权威 + 薄客户端 | ❌ 单机目录 | ⚠️ Hub | ✅ 服务端权威 |
| 索引可重建 | ✅ | ✅ **最干净（无持久派生）** | ❌ | ❌ 双存储 |
| 许可 / 重量 | MIT / 中 | MIT / **最轻** | Apache-2.0 / 重 | **AGPL** / 重（约 47 硬依赖） |

**净结论**：

1. **四个系统全把"原文层"当二等公民**，只有 Hindsight 把 chunks 放进可检索接口。
2. **范式标签预测不了适配，甚至相反**：范式 1 旗舰（OpenViking）最不满足不变量；范式 3 旗舰（Hindsight）反而最接近。
3. **"文件在磁盘上" ≠ "原文逐字保留"**：OpenWiki 是最干净的证据——文件是纯 Markdown、`cat` 可读，**但文件里装的是 LLM 合成**。

### 5.3 在 **D3（VFS 映射式真相源）** 下的核对：五问

D3 把判据从"原文逐字"扩到"**VFS 承载的映射类 + 虚拟类，二者统一可寻址、可授权、可重建**"。据此对两个当前候选：

| # | 要核的问题 | **OpenViking** | **MemOS** |
|---|---|---|---|
| 1 | **VFS 是不是真相源**（删掉索引能否恢复） | ❌ **不能**——官方明说"backups and access controls should account for **both** stores"；memory body 还复制进 vector `abstract`（50KB 上限） | ❌ Neo4j 是 record of record；本地插件 SQLite 内暴力向量，索引不可分离重建 |
| 2 | **路径级读写权限分离**（某子树 agent 只读） | ⚠️ 有 ACL / 多租户（`user_id` + `peer`），但**是否路径级读/写分离未验证** | ⚠️ cube 级 `readable_cube_ids` / `writable_cube_ids` + `CubeShare`；**非路径级** |
| 3 | **虚拟条目能否一等**（场景 1 核心：移动端碎片无磁盘原件） | ⚠️ memory 是虚拟的，**但被 LLM 抽取/合并/改写**，且自定义字段**静默丢弃** | ⚠️ 虚拟（cube），但默认路径 LLM 改写 |
| 4 | **自定义字段可挂可筛** | ❌ 未知顶层字段与已知对象内的未知键**被静默丢弃** | ✅ **强**（任意 `info` key "can be used as filters"、嵌套 `and`/`or`、`gt`） |
| 5 | **写入是否便宜** | ❌ 每次 ingest 必调模型；**强制** embedding + VLM；无零 LLM 路径 | ⚠️ Fast 模式零 LLM，但**是否公开可达未验证**，且文档劝你换成 refined |

**结论（本轮最重要的战略判断）**：

> **没有人同时提供"VFS 寻址 + 路径级权限 + 虚拟条目一等 + 不被 LLM 改写 + 索引可重建"。**
> **D3 想要的形状，在两个候选里都没有现成实现。**

因此任一路线都需要我们**自己加一层**（至少是"虚拟条目怎么写、元数据怎么留、权限怎么分"）——
差别只在**这一层有多薄**。这决定了"用框架"能省下多少（对应 D9 的可行性）。

### 5.4 OpenViking 实测修正（CLI 命令面，2026-10-09，**只读探查，未起服务端、未下载模型**）

安装结果：`openviking 0.4.23` → 隔离环境 `venv-ov/`，**976 MB / 171 个顶层包 / 装了 20.6 分钟**；
入口 `openviking.exe` / `openviking-server.exe` / `ov.exe`；**不需要 Docker**。

**实测推翻/修正了调研阶段的三条判断**：

| 调研阶段的判断 | 实测 | 证据（`ov <cmd> --help`） |
|---|---|---|
| "无导出、可迁移性差，第三方审计记 export ❌" | **错（审计过时）** | **`ov export <uri> <out.ovpack>` / `ov import`**，且 `--include-vectors`（"Include dense vector snapshot"） |
| "双存储、索引不可重建" | **需修正** | **`ov reindex <uri> --mode vectors_only\|semantic_and_vectors`**，**默认比对指纹**、`--force` 才全建；另有 `snapshot`（commit/log/**branch**/diff/restore + `.ovgitignore`）与 `backup`/`restore` |
| "自定义字段静默丢弃、无权限粒度" | **一半错** | **`ov acl`** 是**一等命令**：`get`（direct + effective）、`set --acl-mode restricted`（忽略继承不删）、**`grant <uri> --principal user:x --level read`**、`revoke`；且 **"search within the permitted resource tree"** → **权限直接收窄检索范围**。**但元数据仍只有 `ov set-tags --tags k=v,...`**（字符串、无类型、无校验，挂在文件/目录上） |

**另外确认（对 D3 直接相关）**：
- **`ov add-resource`** 支持**本地文件 / 目录 / URL / 仓库 / 整站（sitemap·RSS）**，可 `--parent viking://projects/<slug>` 或 `--to` 精确落位，`--wait`，**`--watch-interval 1440` 定时刷新** →
  **"真实文件映射"（D3 第①类）有原生入口，且形状就是 `viking://projects/<slug>`**。
- 文件系统面完整：`ls`/`tree`/`mkdir`/`rm`/`cp`/`mv`/`stat`/`attrs`/`get`；分层 `abstract`(L0)/`overview`(L1)/`read`(L2)。
- **`add-memory`（虚拟条目那条路）标注 experimental，且只吃 content、无元数据参数**。
- 异步任务可追踪：`task` / `wait` / `observer`；多租户 `admin` + `--sudo`。

> **关键推论**：**D3 的两类内容，前半（真实文件映射）与 OpenViking 的 `resources` 层原生对应；
> 后半（虚拟条目）对应它的 `memories` 层——而那一层正是"LLM 改写 + 无元数据"的那层。**
> 也就是说：**OpenViking 的 `resources` 层可以用，`memories` 层可以整个不用。** 这解释了为什么直觉上"契合度最高"。
> **待验**：`resources` 的 L2 是否逐字（调研称是**解析后**字节且**默认切块**）——需一次实读比对。

| **元数据过滤契约**（任意 key 可筛、嵌套 `and`/`or`、`gt`） | MemOS | spec §5/§8 最含糊的一环 |

| **`memory_diff.json`**（before/after/deleted_content + `skipped_operations` + 稳定 reason code） | OpenViking | 派生对象审计形态 |
| `since`/`until` + `time_field` | OpenViking | spec §5 `time_range` |
| **`INSTRUCTIONS.md`：人写、机器永不改写** | OpenWiki | 推送层 / 受保护的人写区 |
| **每次调用临时 FTS5、无持久派生索引** | OpenWiki | "索引可重建"的目标形态 |
| ForgetEval（MIT）/ mem0 开放 harness | census | 外部评测锚点 |

## 6. 容量与部署事实

| 事实 | 数值 | 影响 |
|---|---|---|
| 我们方案的模型常驻 | **BGE-M3 1.95 GiB**（perf_70 实测） | **2C2G 放不下**；**本机没问题** |
| 免费机规格 | 阿里云 2 核 2G / **1M 带宽** / 40G 盘（1 年）；另有 ModelScope 免费 CPU 机 | 1 Mbps ≈ 128 KB/s → 拉 2.3GB 模型需 5 小时+；**只够文本级流量** |
| 同宿算术 | OS 0.3–0.4 + agent 后端 0.2–0.4 + 框架 0.5–1.0 + PG 0.5–1.0 = **1.5–2.8 GB** | 2C2G 单机扛不住 |
| 使用习惯 | 本机**基本常开，夜里关机** | 权威点在本机 → **夜里不可用须显式报错**（spec §1 I4） |

**D8 落地**：权威点 = **本机**（数据本就在此、零迁移；Hindsight full 镜像 1.5–2GB 在本机毫无问题）。
免费云机可留作**备份/降级或 agent 后端**，不再是权威点。**备份从"应该做"升级为"必须做"。**
