# Agent 岗能力评判方案（普适模型）

> **用途**：任何"要不要做 / 先做哪个"的裁决，用本模型算 Gap 排序；样本频次见 `docs/jd-baseline.md`。
> **性质**：决策**方法**（模型），不是 ADR、不是实验结论。
> **与 jd-baseline 的分工**：`jd-baseline.md` = 手里的 **样本 census**（4 份 JD 的频次）；本文件 = **可套用到任意 JD 的评判模型**。

## 0. 三个证据源（外部数据为二手统计，标注来源与边界）

| 源 | 内容 | 边界 |
|---|---|---|
| owner 提供的 4 份 JD | 国内 Agent/大模型应用岗（卓望·快手·神州·中城交） | 样本小，见 `jd-baseline.md` |
| **AI Engineering Field Guide**（[role/README](https://github.com/alexeygrigorev/ai-engineering-field-guide/blob/main/role/README.md)）：**6,964 份 JD**，builtin.com，2026-02→08 八次抓取 | 角色类型、技能占比、职责分布 | 单一平台（builtin.com）二手统计，非全市场；趋势有噪声 |
| **EPAM Senior AI Agent Engineer**（[Dice](https://www.dice.com/job-detail/6223c739-7d64-4d62-979d-3dae81871f62)） | 一个**成熟 Agent 岗**的完整职责清单 | 单份，但覆盖面最全 |

### 关键市场数字（引自 Field Guide）

- **角色三分**：AI-First **70.0%** / AI-Support（平台·基础设施·工具）**24.2%** / ML 4.9% —— **同一份 title 下藏着三种岗**。
- **全栈性**：AI-First 岗 **86.8%** 需要 GenAI 之外的技能；只有 **3.9%** 是纯 GenAI；**70.6%** 把 GenAI 与 production/ops（Docker/K8s/CI-CD/MLOps/Terraform）绑定。
- **技能占比**：Python **70.8%** · AWS 40.3% · RAG **39.8%** · **CI/CD 36.8%** · prompt engineering 34.7%。
- **评测**：**59.7%** 的 AI-First 岗**明确要求评测能力**（Field Guide 称之为"the differentiator"）。
- **微调被高估**：只有 **3.6%** 的 AI-First 岗以微调为主要职责，84.6% 完全没提。
- **97.1% 是应用/生产岗**，仅 2.9% 研究岗。

## 1. 模型：三层 + 一道闸门

### L0 前置闸门（Gate，不打分 —— 不通则其余不计分）

**可验证性 = 评测 + 可观测**。owner 判断"评测是任何 agent 优化的前置"，市场与项目内部都同意：

- 市场：**59.7%** 明确要求评测；EPAM 直接把"区分**模型质量问题 vs 软件缺陷**"写成职责。
- 项目：`ADR-0030 D2` 已定 **H（harness/runtime）是 A/B/C 的前置**——同一条规矩同时管项目与简历。

**闸门判据**：`有没有确定性 trace / 回归基准 / 留出集 / 统计口径`。**没有 → 该方向上任何"我优化了 X"都不可验证，简历记 0 分。**

### L1 Agent 内核

| 能力 | 说明 |
|---|---|
| 循环 / 规划 | ReAct / Plan-and-Execute / 代码控循环 / 终止与预算 |
| 工具调用 | tool use / Function Calling / **MCP server** / 契约·权限·审批边界·失败恢复（EPAM 点名） |
| 记忆与上下文 | state persistence / retrieval quality / retention / **isolation between users**；上下文工程 |
| 编排与多 Agent | orchestrator / 委派 / 并行 / artifact 回传 |
| Prompt 与协议 | 输出协议、解析容错、system/角色设计 |

### L2 交付与平台（owner 强调的"兼顾后端与部署"就在这里）

| 能力 | 说明 |
|---|---|
| 服务与接口 | API 设计、异步处理（EPAM 点名） |
| 数据与存储 | 向量库 + 关系库 + 缓存 + 真相源；一致性 |
| 并发/可靠 | 并发模型、性能、retry、recovery、rollback |
| 部署运维 | 容器 / CI-CD / IaC / 云托管服务 |
| **可观测与成本** | logs·metrics·**traces**；**LLM 网关与路由（模型分层、配额、成本控制）**（EPAM 点名） |
| 安全与治理 | authn/authz、安全边界、隔离、审计、red team |

### L3 领域与场景

RAG / 知识库 · 领域适配（金融 · 安全 · 客服）· 技术沟通与 mentorship。

## 2. 证据分级（把"深度"量化）

| 级 | 含义 | 在面试里的表现 |
|---|---|---|
| **E0** | 无 | 不敢提 |
| **E1** | 名词（知道 / 用过工具） | 一问就穿 |
| **E2** | 能独立实现（有代码） | 能过，但不突出 |
| **E3** | 自建 + **数字**（可复现） | 有说服力 |
| **E4** | 自建 + 数字 + **取舍/反例/边界** | 能讲 3 分钟，是区分度来源 |

**简历上只有 E3–E4 计分。**

## 3. 岗位权重向量（按 Field Guide 的三类）

| 画像 | L1 | L2 | L3 | L0 |
|---|---|---|---|---|
| **AI-First 应用岗**（70.0%） | **高** | 中高 | 中 | 闸门 |
| **AI-Support / 平台岗**（24.2%） | 中 | **高** | 低中 | 闸门 |
| **混合岗（实际大多数）** | **高** | **高** | 中 | 闸门 |

> owner 判断"纯 agent 岗还少、一般要兼顾后端与部署"→ 与 **86.8% / 70.6%** 两条统计一致：**默认按"混合岗"配权，按岗位 JD 微调。**

## 4. 决策规则

1. **L0 不通 → 先补 L0**（这解释 H 为何必须先做，也解释 CI/可观测为何值得补）。
2. 其余按 **Gap = W × (E_target − E_now)** 降序投资；Gap 相同取成本低者。
3. **同一格已 E3+ 不再投**（防重复包装）。
4. **简历驱动只能改"排序与措辞"，不能改"做不做"**（场景必要性有否决权）；任何切片无数字与边界 → 简历记 0 分。

## 5. 本项目 Gap 表（据上列规则自评）

| 层 | 能力 | E_now | E_target | Gap | 依据 |
|---|---|---|---|---|---|
| L0 | 评测 harness / trace / 留出集 / CI 统计 | **E4** | E3 | ✅ 已超额 | trace 契约 + `run_hash` + holdout + bootstrap CI（#62） |
| L0 | **自动化回归 CI** | **E0** | E2 | ⚠️ **大且便宜** | 仓库**无 CI**（AGENTS.md 明写）；CI/CD 占比 **36.8%**；EPAM 列 CI/CD 为职责 |
| L1 | 工具调用 / MCP / 权限与审批边界 | **E4** | E3 | ✅ | ACI + `TOOL:` 派发 + 网关 authz + 破坏性操作预览确认（EPAM 的四项全中） |
| L1 | 记忆与上下文 / 用户间隔离 | **E4** | E3 | ✅ | hero；tenant 隔离 + 审计 |
| L1 | 循环 / 规划 | E3 | E3 | 持平 | 代码控循环；无显式 planner |
| L1 | 编排 / 多 Agent | **E2** | E3 | 中 | #60 委派 + #61 组合工具；无 orchestrator（3/4 JD 提到） |
| L2 | 部署运维 | **E4** | E3 | ✅ | 一键部署 Win/WSL + 幂等 + dry-run + 冒烟 |
| L2 | 服务与接口 | E3 | E3 | 持平 | MCP daemon（ASGI）；无独立控制面 |
| L2 | 数据与存储 | E3 | E3 | 持平 | Qdrant + 文件+Git；无关系库/缓存（触发阈值见 jd-baseline §三） |
| L2 | **并发/可靠性（有数字）** | **E2** | E3 | ⚠️ **便宜** | 拓扑设计有，**压测数字没有** |

| L3 | 领域适配 | E2 | E2 | 持平 | 个人知识库场景 |

## 6. 由此得出的优先级（与票对应）

| 序 | 补什么 | 为什么现在 | 成本 |
|---|---|---|---|
| 1 | **CI：一条 workflow 跑 `pytest`（+ 冒烟 SKIP 语义）** | L0 闸门的"回归"半边缺失；Gap 最大且最便宜；命中 36.8% + EPAM | 极低 |
| 2 | **并发/可靠性出一组数字** | E2→E3；后端岗最吃"p95 / 内存 / 长任务阻塞" | 低（一个压测脚本） |
| 3 | **修 #39 真实泄漏 + 回归测试** | E3→E4，且是"我修了真实安全缺陷"的硬证据 | 中低（缺陷已定位） |
| 4 | 可观测性与成本（metrics + 配额 + 模型路由分层） | EPAM 显式要求；我们这块最薄 | 中 |
| 5 | 多 Agent 编排（先轻量：把 #60/#61 讲成委派 + 上下文隔离） | 3/4 JD 提到；重形态需 E 集才能证明 | 中→高 |
| — | **不做**：微调（市场 3.6%）· 纯研究型内容 · 为关键词加 MySQL/Redis（1/4 且"熟悉"级） | | |

## 7. 用法（每次裁决照做）

1. 目标 JD → 判属于哪类画像 → 取权重向量 W。
2. 填 Gap 表（E_now / E_target）。
3. **先看 L0 是否通**；不通先修 L0。
4. 按 Gap 降序 + 成本升序取下一张票。
5. 产出必须带**数字 + 边界**，否则不进简历、也不进基线。
