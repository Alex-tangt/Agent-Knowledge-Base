# 查询改写系统提示词优化实验报告

> 基于 Reflexion 式 LLM 自优化循环的实验记录与分析  
> 数据来源：`backend/optimizer_log.json`

---

## 1. 实验概览

| 项目 | 说明 |
|------|------|
| **目标** | 通过 Reflexion 式 LLM 循环优化查询改写（Query Rewriting）的 system prompt，使改写后的查询在向量检索中取得更好的命中效果 |
| **开发集** | 5 条中文法律咨询查询 |
| **优化轮次** | 7 轮（在收敛前因超时终止） |
| **评估指标** | `norm_delta_best_dist`（归一化最佳距离变化）、`intent_drift`（意图漂移）、`split_count`（子查询数量） |
| **综合评分公式** | `score = 0.7 × norm_delta − 0.3 × intent_drift`，截断至 `[−0.3, 0.7]` |
| **最佳轮次** | **Round 6**，avg_score = **0.0768** |

### Round 1（基线）

```
将用户问题转化为搜索关键词。如问题较复杂，可分解为多条简洁的搜索短语，每行一条。最多5条。
```

- LLM 容易出现"直接回答问题"而非"提取关键词"的行为（见 Q1、Q4 的改写结果）。
- avg_score = −0.0667

### Round 2 ~ 6（关键词限定版）

Round 2 引入限定句后，Round 3~6 保持不变：

```
将用户问题转化为搜索关键词。如问题较复杂，可分解为多条简洁的搜索短语，每行一条。最多5条。每条搜索短语应仅为关键词组合，不含完整句子或解释性内容。
```

- Round 2 引入此 prompt，avg_score 反而下降（−0.1181），主要因 Q4、Q5 的 norm_delta 退化为 0。
- Round 3~6 **系统提示词完全相同**，但输出差异巨大（见下文 LLM 不稳定性分析）。
- Round 6 在完全相同的 prompt 下达到最佳成绩（avg_score = 0.0768）。

### Round 7（尝试解决僵尸查询，未完成）

```
将用户问题转化为搜索关键词。即使问题简短，也必须将其改写为由关键词组成的搜索短语，不得直接复制用户问题原文。如...
```

- Prompt 被截断，导致 LLM 生成退化为单条输出，avg_score 回落至 −0.0581。

## 4. 关键观察

### 4.1 intent_drift 大面积误判

- **26/35（74.3%）** 的评估被标记为 intent_drift=1。
- 其中 **14 个案例** norm_delta > 0.3（改写显著改善了检索距离），但仍被标记 drift=1，导致 score 被惩罚 −0.3。
- **根因**：`eval_service.py` 第 112 行 `intent_drift = await self._check_intent_drift(query, rewritten[0])` 仅取 `rewritten` 列表的**第一个元素**与原始查询做意图比较，忽略了其余子查询。当 rewritten[0] 本身是一条偏向解答的文本时（如 Q2 Round 3 的第一个子查询是长篇法律解释），intent_drift 必然为 1，即使其他 4 条子查询是准确的关键词。
- 以 Q2 Round 3 为例：`rewritten[0]` = "根据《劳动合同法》相关规定，您可能有权获得以下赔偿..."（解释性语句），LLM 自然判定为 drift=1，但整个 5 条 rewritten 的检索效果极好（norm_delta=0.7764）。

### 4.2 僵尸查询："公司无辜把我辞退了我该怎么办"

- 该查询 17 字符，低于 `rag_service.py` 中的 20 字符阈值，**全部 7 轮均未触发改写**，score 恒为 0。
- 这是一个有明确法律意图的短查询（劳动争议 / 违法解除劳动合同），与知识库中的《劳动合同法》高度相关，不应被排除在改写之外。

### 4.3 LLM 不稳定性（相同 Prompt，不同输出）

Round 2~6 的 system prompt **完全相同**，但同一查询的改写输出差异极大：

- **Q2**：Round 2 输出解释性长文（3 段），Round 3 输出更长的解释（5 段），Round 4 输出一条合理改写，Round 5 退回原始查询，Round 6 输出残缺文本"根据《劳动合同法》第"。
- **Q4**：Round 6 获得极佳改写（norm_delta=0.8894），但 Round 2~5 的改写都未能提升检索效果。
- **Q5**：7 轮中有 4 轮 norm_delta=0，仅 Round 3 和 Round 5 有正向提升。

这表明 LLM 对微妙的 query 语义变化和温度/采样随机性高度敏感，单轮评估的结论置信度有限。

### 4.4 Round 6 整体最佳但成因可疑

| Query | Round 6 score | 最佳轮次 | Round 6 是否最佳 |
|-------|--------------|----------|-----------------|
| Q1 | 0.0070 | R5 (0.1050) | ❌ 中度退化 |
| Q2 | **0.3545** | R6 | ✅ 最高（但改写残缺） |
| Q3 | 0.0000 | — | — 僵尸查询 |
| Q4 | **0.3226** | R6 | ✅ 最高 |
| Q5 | −0.3000 | R5 (0.0951) | ❌ 底部 |

Round 6 的总分优势主要来自 Q2 和 Q4 的高分。但 Q2 的高分来自残缺改写 + 运气成分，Q1 和 Q5 的表现反而不如 Round 5。

## 5. 已识别的 Bug 与根因

### Bug 1：intent_drift 仅检查 rewritten[0]

| 项目 | 详情 |
|------|------|
| **位置** | `backend/services/eval_service.py:112` |
| **代码** | `intent_drift = await self._check_intent_drift(query, rewritten[0])` |
| **问题** | 当 rewritten 包含多条子查询时，仅用第一条做意图判断。若第一条碰巧是解释性/冗余的子查询（与 LLM 生成顺序有关），整组改写被误判为 drift |
| **影响** | 26/35（74.3%）标记 drift，其中 14 个案例 norm_delta > 0.3 的优秀改写被严重惩罚 |
| **建议修复** | 拼接全部 rewritten 后再做意图判断，或分别判断后取 mean |

### Bug 2：20 字符阈值阻碍短查询改写

| 项目 | 详情 |
|------|------|
| **位置** | `backend/services/rag_service.py` 第 281 行附近 |
| **代码** | `if len(query) < 20:` → 跳过改写 |
| **问题** | "公司无辜把我辞退了我该怎么办"（17 字）被永久排除在改写之外 |
| **建议修复** | 降低阈值至 5~10 字符，或改为可配置参数，或完全移除硬阈值 |

### 问题 3：关键词改写与 intent_drift 的内在冲突

- 关键词改写（keyword-only rewriting）的设计目标就是将自然语言查询压缩为搜索关键词，**必然丢失原始查询的完整句子结构**。
- 当前 intent_drift 检测用 YES/NO 二元判断，LLM 看到一个关键词列表（无完整句式）时大概率判 NO → drift=1。
- 这是一种**结构性冲突**：优化目标（norm_delta ↑）与惩罚项（intent_drift ↓）相互矛盾。

## 6. 推荐修复（按优先级排序）

### P0 — 修复 intent_drift 检测逻辑

```python
# eval_service.py:112 — 修改前
intent_drift = await self._check_intent_drift(query, rewritten[0])

# 修改后
rewritten_concat = " | ".join(rewritten)
intent_drift = await self._check_intent_drift(query, rewritten_concat)
```

或将所有子查询分别判定后取 majority vote。此修复预计可消除 74% 的 drift 伪阳性。

### P1 — 降低或移除 20 字符阈值

```python
# rag_service.py
MIN_QUERY_LENGTH_FOR_REWRITE = 5  # 从 20 改为 5，或改为可配置
```

或完全移除硬阈值，改用"改写后与原查询的语义相似度"来判断是否需要改写。

### P2 — 替换 intent_drift 评估方式

考虑以下替代方案：
- **检索结果语义重叠度**：比较 original query 的 top-k 检索结果与 rewritten query 的 top-k 检索结果的重合率
- **回答质量对比**：用 LLM-as-judge 评估改写前后 RAG 回答的质量差异，而非仅做二元意图判断
- **调整评分权重**：如果当前设计确定保留 intent_drift，可将权重从 −0.3 降至 −0.1，减少对关键词改写的结构性惩罚

### P3 — 降低噪声，提高评估可靠性

- **扩大开发集**：当前 5 条查询量过小，难以得到统计显著结论
- **多次运行取均值**：同一 prompt 对同一查询运行 3~5 次，取各指标均值，消除 LLM 随机性
- **加入 reranker 分数阈值校准**：当前 RELEVANCE_THRESHOLD=0.85 未在 optimizer 中考虑
