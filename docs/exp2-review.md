# Exp2 Review: 查询改写优化器实验失败分析

> 实验日期：2026-07-24 ~ 2026-07-25  
> 状态：提前终止 / 未产出可用优化结果  
> 实验代码：`backend/optimizers/rewrite_optimizer.py` v3

---

## 1. 实验目标

通过 Reflexion 式 LLM 自优化循环，迭代改进查询改写（Query Rewriting）的 system prompt，使改写后的搜索查询在向量检索中取得更好的命中效果。

核心评估指标：

| 指标 | 定义 | 方向 |
|------|------|------|
| `norm_delta` | `(best_dist_orig - best_dist_rewrite) / best_dist_orig`, clamped to [0,1] | 越大越好 |
| `intent_drift` | 改写后是否丢失原始 query 信息需求，v1 为二元 0/1，v3 改为连续 0.0~1.0 | 越小越好 |
| `score` | `0.7 × norm_delta - 0.1 × intent_drift` (v3), clamped to [-0.1, 0.7] | 越大越好 |

## 2. 实验设计

### 2.1 管道架构

```
dev_set (16 queries)
  → 改写 LLM (stateless, current prompt) → rewritten[]
  → 检索 (Qdrant, pool=30) + Reranker (bge-reranker-v2-m3, CPU)
  → 意图判断 LLM (stateless, intent_drift scoring)
  → score = f(norm_delta, intent_drift)
  → 优化 LLM (stateful, conversation_history) → {analysis, new_prompt}
  → new_prompt → 下一轮
```

### 2.2 参数配置

| 参数 | v1 值 | v3 值 | 变更原因 |
|------|-------|-------|----------|
| 检索池大小 | 100 | 30 | CPU 性能瓶颈 |
| 最多子查询数 | 5 | 3 | 同上 |
| intent_drift 权重 | 0.3 | 0.1 | 缓解关键词改写结构性惩罚 |
| intent_drift 类型 | 二元 YES/NO | 连续 0.0~1.0 | 提升区分度 |
| 优化 LLM max_tokens | 600 | 1500 | 防 JSON 截断 |
| Dev set 大小 | 5 | 16 | 增加统计显著性 |
| 优化 LLM 输出格式 | `[OLD]/[NEW]` | `{analysis, new_prompt}` | 结构化管理 |

### 2.3 Dev Set 构建

源池：`tests/questions.md` 53 条（25 事实型 + 16 综合型 + 12 无答案型）

筛选策略：排除无答案型 → 按 `best_dist_orig` 降序 → 取 `orig_dist ≥ 0.01` 的查询 → 补充原始 3 条高难度查询。

最终 dev set：16 条，`best_dist_orig` 覆盖范围 [0.0117, 0.8735]。

### 2.4 LLM 实体隔离

| 实体 | 状态 | 角色 |
|------|------|------|
| 改写 LLM | 无状态 | 接收 prompt + query → 输出搜索关键词 |
| 意图判断 LLM | 无状态 | 接收原 query + 改写后关键词 → 输出意图偏移分数 |
| 优化 LLM | 有状态（messages 数组） | 接收每轮 JSON metrics → 诊断 + 提出新 prompt |

三者共享同一 OpenAI client（API key / model），但会话上下文完全隔离。

## 4. 失败模式分类

### F-1: intent_drift 结构性失效（严重度：致命）

**现象**：v1 实验中 15/16 (93.8%) 的查询被标记为 intent_drift=1，包括大量明显正确的关键词改写。v3 改为连续打分后未在实验中验证。

**根因**：二元 YES/NO 意图判断与关键词改写之间存在不可调和的结构性矛盾。意图判断 LLM 的 prompt 设计为比较"完整句子 vs 完整句子"，当接收到关键词列表时（`"违法解除劳动合同 赔偿标准 | 被公司无故辞退 如何维权 | 劳动仲裁 申请流程"`），LLM 几乎必然判定为"意图漂移"。这不是 LLM 能力问题，而是 prompt 设计假设错误。

**证据**：
- Q1 "公司违法辞退员工…救济与赔偿？" → `"违法解除劳动合同 赔偿金 经济补偿 | 劳动合同法 第四十八条 第八十七条 | 劳动仲裁 违法辞退 救济途径"` — norm_delta=0.9912（接近完美检索），但 drift=1，score 从 0.69 被罚到 0.39
- Q11 "劳动合同法对试用期工资有哪些限制性规定？" → `"试用期工资 限制 劳动合同法 | 试用期 工资 规定 | 试用期工资 最低标准"` — norm_delta=1.0（完美），drift=1，score 从 0.70 被罚到 0.40

**影响范围**：所有基于关键词改写的查询。在 v1 权重 0.3 下，intent_drift=1 惩罚等同于 norm_delta 需要额外 0.43 才能抵消，显著压低所有 score。

### F-2: 改写 LLM 行为不可控（严重度：高）

**现象**：改写 LLM 频繁输出**完整法律解答**而非搜索关键词。

**典型例子**：
- Q4 "某APP未经同意收集个人信息…" → 改写为 4 段法律建议：`"根据《中华人民共和国个人信息保护法》，您可以要求该APP：- 停止收集并删除已收集的个人信息（依据第47条）..."`
- Q14 "公司没签合同工作6个月…" → 改写为 199 字法律解答：`"根据《中华人民共和国劳动合同法》第十条规定…建议收集考勤记录、工资流水…"`

**根因**：改写 LLM 的 system prompt 未包含充分的输出格式约束。基线 prompt `"将用户问题转化为搜索关键词"` 太过模糊，LLM 倾向于将"转化"理解为"回答"而非"提取关键词"。

**影响范围**：12/16 查询在 Round 1 出现不同程度的解答式输出。

### F-3: 部分查询不触发改写（严重度：中）

**现象**：3/16 查询在 Round 1 中改写结果 = 原始查询（未触发改写）。

- Q5 "独生子女…专项附加扣除…" (Round 1 & 2)
- Q15 "干了2年老板不让来了一分没给…" (Round 1)
- Q3 "消费者购买机动车…反复维修…" (Round 2)

**根因**：LLM 将部分口语化查询判定为"已经是搜索关键词"或"太复杂无法压缩"，直接原样返回。当 query 包含多层嵌套条件时（独生子女 + 小学孩子 + 父母60岁 + 租房 + 无自有住房），改写 LLM 的选择是"不动"。

**影响**：这些查询的 norm_delta=0，对优化器来说是不可优化的盲区。

### F-4: 低 orig_dist 查询的改写退化（严重度：中）

**现象**：orig_dist < 0.03 的查询（#9~#13），改写后检索距离反而变大。

| Query | orig_dist | Round 1 rw_dist | Round 2 rw_dist |
|-------|-----------|-----------------|-----------------|
| 未成年人网络欺凌 | 0.0290 | 0.0240 (改善) | 0.0572 (退化) |
| 住房贷款利息扣除 | 0.0229 | 0.0103 (改善) | 0.0664 (退化) |
| 试用期工资规定 | 0.0161 | 0.0000 (改善) | 0.0142 (小幅改善) |
| 食品经营许可 | 0.0128 | 0.0005 (改善) | 0.0164 (退化) |
| 正当防卫界限 | 0.0117 | 0.0052 (改善) | 0.0080 (改善) |

**根因**：低 orig_dist 的查询原本就能精确定位到知识库片段（如法条原文），改写引入的关键词反而干扰了语义匹配。Round 2 的 prompt 要求"禁止完整句子，只用关键词"，导致原本能精准匹配法条的查询（如"住房贷款利息专项附加扣除每月可扣除多少元"）被压缩为模糊关键词，检索精度下降。

### F-5: 优化 LLM 响应截断（严重度：高）

**现象**：Round 2 优化 LLM 的 JSON 响应在 `new_prompt` 字段中间被截断。

```
{"analysis": "...", "new_prompt": "将用户问题转化为搜索关键词短语，用于法律知识库检索。要求：\n1. 仅输出关键词短语，每行一条，最多3条。\n2
```

**根因**：`max_tokens=800` 不足。优化 LLM 生成了完整的 `analysis`（约 200 中文字符）+ 完整的 `new_prompt`（约 400 中文字符），在 `new_prompt` 的第 2 条规则的 `2` 之后被截断。

**连锁反应**：JSON 解析失败 → `_parse_response()` 返回 `(None, None)` → `new_prompt is None` → 触发"放弃"逻辑 → 优化在第 2 轮终止。一次 token 截断导致整个实验提前结束。

### F-6: Qdrant 本地模式锁冲突（严重度：高）

**现象**：`final_validate()` 中 test set 的 5 条查询全部失败，错误信息：

```
Storage folder is already accessed by another instance of Qdrant client.
```

**根因**：`final_validate()` 调用 `self._get_eval_service()` 创建了**第二个** `EvalService` → 第二个 `RAGService` → 第二个 `VectorStoreService`，而主优化循环中第一个 `VectorStoreService` 仍持有 Qdrant 本地模式的排他锁。

**影响**：test set 5 条查询全部 `score=0`，最终验证完全无效。无法判断优化 prompt 是否在 dev set 上过拟合。

## 5. 根因分析

### 5.1 核心矛盾：评估指标与被评估对象的不匹配

本实验的评估目标（"改写后的搜索关键词能否检索到更好的文档"）与评估手段（"意图判断 LLM 比较原始 query 与改写后的关键词"）之间存在根本性错位：

1. **norm_delta 的测量尺子不统一**：原始 query 和改写后 query 的 reranker 分数对着**不同的文本对**计算（原始 query × chunks vs 改写 query × chunks），rendering 直接比较无效。Spec 要求"用原始 query 统一 rerank"，但代码未实现。

2. **intent_drift 的 prompt 假设错误**：二元 YES/NO 判定预设"改写前后的文本形态一致"，忽略了"自然语言问句 → 关键词列表"这种合法且必要的形态转换。

3. **score 公式的自洽性**：`0.7×norm_delta − 0.1×intent_drift` 的设计意图是"检索提升为主，意图保留为辅"，但两个指标测量的是不同尺度的量（一个用 reranker 距离，一个用 LLM 主观判断），加权求和缺乏量纲统一的数学基础。

### 5.2 工程瓶颈：CPU 环境下的评估速度

| 环节 | 每次耗时 | 每轮次数 | 每轮总耗时 |
|------|----------|----------|------------|
| 改写 LLM 调用 | ~3s | 16 | ~48s |
| 检索 (Qdrant) | ~0.1s | 16×(1+avg3)≈64 | ~6s |
| Reranker (CPU) | ~10-25s | 64 | ~10-15min |
| 意图判断 LLM | ~1s | 16 | ~16s |
| 优化 LLM | ~5s | 1 | ~5s |

每轮总耗时 ≈ 15-20 分钟。10 轮上限 = 3.3 小时。若 pool=100（spec 要求），每轮 40-50 分钟。在此时间约束下，任何实验性问题（JSON 截断、锁冲突、prompt 设计缺陷）都会导致数小时的损失。

## 6. 经验教训

### 6.1 评估指标设计

1. **二元分类指标不适用于渐进式优化目标**。intent_drift 的 YES/NO 判定在关键词改写的语境下几乎没有区分度（93.8% drift rate），导致该指标退化为常数惩罚项，失去优化引导价值。

2. **跨模态 LLM 判断的不可复现性**。意图判断 LLM 的输出即使 temperature=0 也不能保证确定性（尤其是不同 model 版本之间）。将不可复现的指标纳入优化目标公式，使得任何 score 变动的归因模糊：是 prompt 改好了还是 judge 随机波动了？

3. **复合指标需要在单一测量系统内统一定标**。norm_delta 和 intent_drift 分别来自 reranker（向量距离）和 LLM（语义判断），两者的数值分布和波动特性完全不同，无法通过简单加权求和形成有意义的综合评分。

### 6.2 优化管道设计

4. **被优化对象（改写 LLM）与评估对象（检索系统）之间的因果链过长**。改写 prompt 的一处修改 → 改写 LLM 的输出变化 → 检索命中变化 → reranker 距离变化 → score 变化。链路中的每一步都可能引入噪声，且每步的 noise floor 可能超过有效 signal。

5. **优化 LLM 只能通过 score 间接感知改写质量**，无法直接查看改写文本（v1 设计）。优化 LLM 对"改写 LLM 到底输出了什么"的判断完全依赖数字，而数字已被 intent_drift 严重污染（v1 中 drift=1 几乎全覆盖）。

### 6.3 工程可靠性

6. **令牌限制（max_tokens）是硬故障点**。当输出被截断时，不应触发"放弃"逻辑——截断 ≠ 放弃。

7. **排他锁管理是状态管理的盲区**。Qdrant 本地模式的单实例约束未被纳入状态管理设计——同一进程中出现了两个独立创建的 `VectorStoreService` 实例。

## 7. 改进方向

### 7.1 评估指标的重新设计（优先级：P0）

- **去掉 intent_drift**，或将其降级为描述性指标（仅记录，不参与 score 计算）
- **统一 norm_delta 的测量基准**：所有检索结果用**原始 query** 做 reranker 统一打分
- 考虑引入**检索结果重叠度**（Jaccard / nDCG of top-k 文档集合）作为可计算、可复现的替代指标

### 7.2 优化策略的简化（优先级：P1）

- 当前的迭代式优化（10 轮 × 20 分钟/轮）在 CPU 环境不可行
- 替代方案：单次分析 —— 跑一轮完整评估，将逐 query 的改写文本 + metrics + 原始 query 一次性发给优化 LLM，让它 output 最终的优化 prompt
- 或：将优化实验移至 GPU 环境（reranker 在 GPU 上速度为 CPU 的 20-50 倍）

### 7.3 改写 LLM 的行为约束（优先级：P1）

- 当前 prompt 对输出格式的约束太弱，需加入硬性格式要求
- 建议：在 system prompt 中增加反例（`"不要输出：根据《XXX法》第X条规定..."`）和输出模板（`"输出格式：关键词1 | 关键词2\n法条编号"`）

### 7.4 工程健壮性（优先级：P2）

- JSON 解析失败不应等同于 `new_prompt=null`（放弃），应区分"格式错误"和"主动放弃"
- Qdrant 本地模式加锁检查：在 `_get_eval_service()` 中检测是否已有活跃实例

---

## 8. 结论

本实验在以下核心设计假设上存在缺陷：

1. **intent_drift 作为评估指标的设计假设**（二元判定适用于关键词改写）被实验数据证伪
2. **迭代式优化在 CPU 环境的时间可行性**被实际运行数据否定（每轮 15-20 分钟）
3. **norm_delta 的跨 query 可比性**因 reranker 打分基准不统一而存疑

在评估框架本身的可信度未建立之前，优化 LLM 的任何 prompt 迭代都缺乏可靠的反馈信号。建议下一阶段聚焦于评估指标的重设计（P0），在验证指标有效性的基础之上，再考虑优化策略。
