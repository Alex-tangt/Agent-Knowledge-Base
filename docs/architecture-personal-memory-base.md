> **推荐形状：家用 PC 上一个现成 VFS 管理的个人原文库，项目文件只读映射，手机提交的内容直接成为 VFS 条目，底层保存、权限、来源追平与恢复由选定实现承接。本仓保留 agent 接入和评测。第一步在隔离副本上跑通一条保存 → 原文读回 → 第二消费者读取的真实链路。**

## 1. 本质权衡：减少自维护，同时保住内容语义

这是**服务端权威的个人内容仓库（content repository），带只读来源挂载与派生检索**。这里的“服务端”可以就在家用 PC 上。多个设备访问同一权威点，不增加同步副本、离线写入和冲突合并机制。

本轮最关键的权衡是：**把管理交给现成实现能省多少工作，为保住原文、映射与权限又要补回多少工作。** 若在框架外重新维护正文主库、来源同步、ACL、版本与恢复，就没有真正完成管理责任的移交。

S1 要求各 agent 共享同一份人的记忆，**不推出单写者、一个 agent 独占写权限或唯一写入入口**。多个授权 agent 都能向同一 VFS 写入，由选定实现保证操作一致性。项目来源只读来自 S2 对映射类的具体约束，不能推广为所有条目的单写者规则。VFS 统一的是地址和操作语义，不要求所有对象住同一个物理目录。

第二个权衡是**集成成本与控制权**。你们要减少的是安装、升级、排障、恢复和适配的总工作量。依赖少、术语漂亮、功能多，都不能单独证明更省维护。

## 2. 实现归属：现成 VFS 管理底层，本仓保留接入与评测

| 模块 | 职责与接口 | 应交给现成实现的部分 |
|---|---|---|
| 原文与版本 | 管理自有原文、只读来源挂载、来源版本与证据快照；原文写入不调用 LLM | 文件或标准对象存储、版本工具、备份工具 |
| 统一访问 | 地址解析、范围列举、凭证身份、读写授权、幂等写入、明确错误；向 MCP/HTTP 暴露小接口 | 传输、身份验证与 ACL 的可靠实现，能直接配置就不重写 |
| 派生检索 | 根据原文与版本建全文/向量索引，报告覆盖范围与新鲜度；删除索引后能够重建 | 检索引擎、编码器、排序算法 |

上下文装配留在各 agent：什么时候搜索、读哪些原文、预算多少、如何生成回答。基座提供引用与状态，避免依赖某个宿主的上下文格式。

**现有实现已经基本具备上表的职责，所以上表不是新的架构增量，也不是继续演进旧引擎的理由。** 真正的变化是归属：让现成 VFS 承接存储、目录、权限、来源更新、索引和恢复；本仓只维护必要接入与外部验收。第一期采用选定实现的单机部署，不人为增加模块或进程。

原来的四层划分大体合理，但“文件/对象 + 索引”应在语义上分开，因为两者的恢复要求不同；“上下文装配”目前属于消费者。最值得钉住的接缝是**消费者访问原文与检索结果的接口**，无需再造通用存储框架。

## 3. 两类内容：同一地址空间，两种写入规则

| 地址示例 | 权威与操作 |
|---|---|
| `/projects/agent-kb/docs/adr/...md` | 指向注册 repo 的文件；基座只读，原作者仍在 repo 修改 |
| `/captures/2026-10-10/article/<id>.md` | app 直接创建 VFS 条目，由选定实现原样保存；对授权 agent 追加开放，既有原件禁止 LLM 覆盖改写 |
| `/captures/2026-10-10/video/<id>.md` | 同上；入库前没有磁盘文件，不影响成为一等 VFS 条目 |

**推荐让虚拟类直接成为现成 VFS 管理的条目，底层文件或 DB 由该实现选择。** 不要求 app 或本仓另外维护一套文件主库、git 仓库、sidecar 和同步逻辑。如果具体实现只能导入文件，可在接入时使用临时输入文件；它不成为另一份权威正文。手机生成的总结就是本次提交的原文；保留它不等于已经保存或验证了视频、文章本身，出处仍需记录。

路径中的日期定义为**本人接触日期**，按 Asia/Shanghai 解释；补录昨天的内容仍落昨天的路径。类型取明确路径段。入库方提供日期，基座校验，不能用接收时间或文件 mtime 替代。

主题范围若不能靠项目子树表达，用一个指向条目 id 的小清单表达，例如主题路径解析为这些引用的视图。**不复制正文到多个主题目录。** 视图授权仍检查对象的规范地址，主题入口不能扩大权限。首期只实现实际需要的一份主题清单。

普通文件的优势是可外部阅读和携带；不足是多文件变更、幂等与一致快照需要可靠实现。标准 DB 中的原文对象也完全成立，能利用事务，但恢复要带 schema、版本与配置，导出要保证原文字节和引用无损。“只能通过某产品查询才存在的无原件对象”会增加恢复负担，当前没有必要。

这些是实现内部的取舍，不应重新变成使用者的日常管理任务。采用 VFS 的实际收益应包括：使用者只面对路径与内容，来源跟踪、索引状态、历史与备份按配置自动维护。

第三种做法是**对象与路径分开**：原文按稳定 id 保存，路径只是目录清单中的定位。这允许之后换文件/DB 实现而不变更引用。现在保留这种区别即可，不做通用内容寻址存储；版本用内容哈希标识，不把内容哈希当条目的永久身份。

### 项目资料的漂移怎么处理

停止新增与 repo 正文平行、可独立编辑的项目总结作为权威资料。现有手写总结先保留，不自动删除或改写；将它们视为另一个历史输入，逐步明确对应的源文件与版本。

未来摘要另存，引用输入的 `id + revision`。源变化后标记摘要过期，不能假装两份内容已经同步；是否重新生成属于后续学习层。**索引可以自动追平，摘要不能冒充原文。**

版本标识、过期检测和历史记录由实现自动维护，不以人专门审查 diff、整理版本或审批每次写入为前提。历史首先用于误写、故障和恢复；当前使用仍按普通路径读到当前有效内容。若需要人工持续维护清单才能自洽，就没有解决你们提出的管理负担。

映射来源的当前读取返回源文件内容；已使用版本的不可变快照可用于历史引用与恢复。快照没有第二写入入口，因此不形成双份权威。来源失联时，当前读取报错；历史版本可以明确读取快照，不能把旧快照冒充当前来源。

## 4. 最小接口：五项操作，包含行为而不只是方法名

```text
Ref = {id, path, revision, source_ref, writable}
list(scope, cursor)                    -> refs + completeness
get(id, revision?)                     -> original_bytes + source_state
append(path, original_bytes, request_id) -> ref + durable_receipt + index_state
search(query, scope, limit)            -> refs/snippets + coverage + index_state
status(scope)                         -> availability + source/index/job_state
```

上述接口是行为验收模型，**不要求在现成 VFS 外再实现一套五方法管理层**。原生工具能直接表达语义就直接接入；只有消费者确实需要时才做薄适配。

身份来自凭证，调用方不能自行指定。`scope` 采用路径或路径集合；首期明确请求未授权子树就报权限错误，不把拒绝访问变成空结果。省略范围时默认查询该身份的允许范围，并返回 `effective_scope`；完整性只针对这个实际范围作承诺。`list/search/status` 采用同一规则。权限同时覆盖目录、计数、搜索片段、原文和写入，不能只靠 skill 规劝。挂载路径规范化与实际来源约束交给这一模块，不能经别名、路径穿越或符号链接越过授权范围。

`list/get` 不依赖向量索引。`search` 是候选发现，`get` 是指定版本的原文读取；搜索命中的片段必须能回到同一版本。若源文件已经变化，要明确提示或重新查询，不能用新正文无声支撑旧片段。

`append` 的成功指原文与回执已经持久保存，索引可以仍是 pending。超时后用同一 `request_id` 重试得到同一结果；相同请求 id 携带不同正文必须冲突报错。元数据或清单不能在序列化时悄悄改变原文；用写前、读回哈希验收。

`id` 是对象身份，`path` 是定位，`revision` 是正文版本。首期固定挂载与源文件相对路径；文件改名需显式登记，暂不自动推断身份连续性。后续移动、取代、归档沿用稳定引用，按真实需求增加操作；修改时再引入预期版本，避免覆盖别人刚提交的内容。

权威点断连、来源失联、权限不足、索引失败必须区分。首期采取严格行为：声明范围查不完整就报错；只有源可达、授权范围完成枚举且索引覆盖已确认，才能把空结果解释为本次检索无命中。即便如此，无命中也不证明语义上没有相关知识。

新 agent 首次接入至少实际读取一份短接入说明：可访问范围、搜索/读取方法、失败行为、应在何时检索。它可通过宿主支持的启动注入或 skill 中的首次读取动作完成。**注册工具只解决可调用，共享持久层只解决可获得；实际使用仍需宿主接入验收。** 不在启动时灌入全部记忆。

## 5. Build vs buy：自持契约，采购实现

你们的假设需收窄：“记忆语义必须自持”应指**你们决定规则并拥有验收**，不意味着 ACL、版本管理、日志和存储都要亲自实现。

当前必须掌握的规则很少：原文不改写、项目来源只读、路径范围、agent 授权、稳定引用、持久写入回执、故障显式。它们可以大部分通过现成实现的配置表达。解析、编码、全文检索、向量检索和备份机制直接复用成熟实现。

所以我支持冻结旧引擎；同时，**不把冻结旧引擎等同于必须采用一整套“学习型记忆系统”。** 对这个规模，一套现成文件资源子系统或标准存储/检索组合可能比完整记忆产品更合算。若框架实际承接了权限、版本、恢复、检索，较重的依赖也可能值得；不能只数包体。

对当前已安装候选，先验证它的原始文件/资源操作能否直接承载映射类和虚拟条目；原文提交不必进入自动抽取改写通道。若需要文件导入，仅把文件作为接入输入，导入后由 VFS 管理，**不保留一套需要双向同步的外部主库**。这是待验证的接入假设，本文没有证明该产品满足它。

如果适配时需要改框架核心、拦截它的改写、维护双套正文，或自行补写大半权限/版本/恢复机制，就说明没有买到主要维护收益，应停在探针阶段。那时重新选择更薄的现成实现，不恢复旧引擎演进，也不继续扩大产品清单。

## 6. 可替换性：保住数据出口与消费者接口

值得支付的成本是两项：

- **数据可退出**：原文字节、稳定 id、来源/版本、路径清单、生命周期与授权配置都能恢复或无损导出；凭据另行安全保存或重发。
- **消费者稳定**：agent 通过上述行为契约访问，后端不外溢到 skill 和 agent 循环。MCP 是传输/工具协议，具体这些语义仍需要契约测试。

不用要求所有后端都提供相同的快照、查询语言或分层摘要。后端可以使用自己的索引、压缩和任务机制；只要它不能改变原文语义，且恢复/导出兑现。现在一个后端实现就够，不为尚不存在的第二后端做大型插件体系。

“数据可带走”和“热切换两个内核”是不同成本。当前需要前者和一个干净的消费者接缝，热切换没有实例需求。

## 7. 已知先例：借三个机制，不照搬一个大系统

**问题类是内容仓库与搜索读模型**；个人是所有权，家用 PC 是部署选择。下列机制仅解释选定实现内部可以怎样组织内容，不构成本仓重新实现文件/git/索引组合的施工建议。

可以直接借用的机制：

- **Git 的对象与目录分离**：blob 保存内容，tree 表达文件名与目录关系。借它理解路径与版本，不必自行实现一套 Git。[Git 官方对象模型](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- **SQLite FTS5 的内容与索引分离**：external-content 模式在同一数据库内索引另一张表或视图，并提供 rebuild。借它设计可重建读模型；它不是自动索引任意文件目录，外部文件变化仍需收录实现维护。[SQLite 官方 FTS5 文档](https://www.sqlite.org/fts5.html#external_content_tables)
- **读写模型分工**：原文写入与搜索读取可以采用不同表示。这里只需一个派生索引；Fowler 的说明也提醒全面采用会增加复杂度，无需引入事件总线与事件溯源平台。[Martin Fowler 的 CQRS 说明](https://martinfowler.com/bliki/CQRS.html)

这些是架构类比与成熟机制，**不是声称已有一个产品完整满足 S1–S3**。若用 FTS5，中文检索要实际验短词和长句：默认 unicode61 按连续字符成词，不能假设已完成中文分词；选择现成分词/子串检索方案，不自造排序算法。[SQLite 官方 tokenizer 说明](https://www.sqlite.org/fts5.html#tokenizers)

## 8. 一周落地路径：有条件的计划，不承诺尚未跑通的后端

| 阶段 | 交付与停止条件 | 本期必须留下的接口 |
|---|---|---|
| 第 1 天：契约探针 | 隔离副本，一个 repo 文件、一条 app 输入；真实服务保存/读回哈希一致，另一消费者读到；删派生索引后原文仍可读并可重建索引。服务起不来或要求核心 fork，就停下处理具体阻塞，不继续设计上层 | `Ref`、`get`、`append` 与明确错误 |
| 第 2–4 天：最小可用 | 一个只读 repo，文章/视频各两条，两个 agent 身份，第二设备访问；按日期/类型路径枚举，一份实际主题清单，基础全文检索；写后跨入口可见、重复提交不重复、范围权限同时约束列举/搜索/读取/写入 | `scope`、`request_id`、`list`、`search`、`status` |
| 第 5–7 天：恢复与接入 | 真正注入/读取首次接入说明；模拟 PC 停止、来源失联、索引失败与落后；备份到另一介质，在空数据根恢复，重新跑关键合同验收 | 数据导出清单、来源版本、授权配置、失败/任务状态；备份恢复先用运维命令 |
| 演进：出现真实需求后 | 全文确实漏召回再接语义检索；实际发生取代/归档再扩生命周期；学习层只写另存派生物，引用输入版本 | 已有 `search` 接缝；新增变更操作的预期版本；未来派生物引用 `id + revision` |

MVP 保留原文、路径范围、读写权限、自动历史/恢复、备份和显式故障；不要求人日常审查历史。先不做自动摘要、画像、复杂调度、离线同步、通用后端插件或检索算法优化。语义检索是后续补召回的能力，不阻塞保存与原文读取。这些能力优先验证现成 VFS，而不是在旧引擎上补齐。

映射来源的版本与原文字节也在恢复范围，不能只备份基座自写目录。Git 历史不是异盘备份；索引不是原文备份。备份要形成一致检查点，再复制到另一介质；历史快照恢复不代表当前 repo 已重新挂载，后者另验。若采用 SQLite，可使用它的在线备份机制取得一致快照，而不是盲拷正在写的数据库文件。[SQLite 官方 Backup API](https://www.sqlite.org/backup.html)

这是一条目标为一周的纵向切片。候选服务仍未启动，**第 1 天是否通过决定后续日期是否成立**。不把原有单测数量当作新后端验收；保留评测集和 trace，新增薄契约驱动，测试从外部接口进入。

旧引擎、真实 KB、真实索引不在这次迁移探针中修改。迁移真实数据和切换生产入口，应等合同证据齐全再做。

## 9. 你们问错或问大的问题

1. **“统一 VFS 是否必须统一存储？”** 应问每个对象的权威在哪里、谁能修改、引用锁定哪个版本。统一地址与统一物理机制是两件事。
2. **“没有磁盘原件，所以得支持特殊虚拟记忆对象？”** 没有前置文件只是入口差异；接收后存成文件已经满足需求。特殊 memory API 不应成为先决条件。
3. **“换内核必须显著提高检索质量？”** 如果目的在减少维护，这不是合适的主判据。应验收语义无损、代表性任务够用和维护面减少。旧预注册 J1–J5 保留；新契约探针另立目的与判据，不事后改旧实验标准。
4. **“同一份持久记忆会让新 agent 自动懂我？”** 它让知识可获得；宿主是否实际读取、何时检索、如何采用，要靠接入面与任务验收。学习层不能替代这一点。
5. **“摘要与 repo 同步好就没有漂移？”** 双份可编辑权威才是病根。保留一个原件，让摘要带版本引用和过期状态，才能把问题变成可控制的派生更新。
6. **“目录 + 搜索 + 备份是不是太简单？”** 存储可以这么简单。真实存在的额外工作是多入口授权、幂等提交、来源失联、新鲜度与可恢复性；这几项不能用目录名称或 skill 替代。超出这些的通用机制可以等真实实例。

我的判断：**需求存在，平台化冲动可以砍掉。** 你们已经有跨入口采集和跨项目读取；先把这两个使用链路及它们的失败路径跑通，就有一个能用、能解释、能接续的记忆基座。

## 10. 选择性复用：先选公开能力，再考虑拆模块

2026-10-10：owner 认可 MVP 验证方向，并请求指导如何按需纳入 OpenViking / MemOS 能力。以下仍是接入建议，**没有实施，也没有证明已安装版本可用**。产品事实核对的是当前官方 main / 在线文档，不等同于隔离环境中的 OpenViking 0.4.23。

### 完整框架接入的默认顺序

1. **配置与公开操作**：使用官方支持的处理模式、开关、MCP/HTTP/SDK；框架正常安装，不用删除内部源码来裁剪功能。
2. **薄适配**：只翻译现有 agent 工具与公开能力之间的参数、引用、结果和错误。服务端授权不能被适配层绕过；也不直接修改底层文件或 DB 表。
3. **已文档化的独立模块**：出现具体任务后，验证模块能否通过配置构建、独立返回结果，并在隔离环境运行。一个目录名或 optional extra 本身不证明模块可独立使用。
4. **源码借鉴与受控 fork**：如果愿意接手一个明确范围的维护责任，直接复用并裁剪上游代码可以成为正式候选路线，范围不必局限于小算法。应取出完成一项能力所需的代码、依赖和测试，验证裁剪后的正确性与净维护收益。具体办法见下一节。

### 能力取用地图

| 能力 | 默认选择 | 何时引入 / 验什么 |
|---|---|---|
| 资料寻址、原文读取/创建、范围检索、访问控制、恢复 | 先由 OpenViking 的公开资源面验证承接 | MVP；原样往返、来源追平、权限、故障与恢复需真链路证明 |
| 资源导航摘要 / 会话意图规划 / 长期记忆抽取 | 首期只开启当前任务需要的处理 | 能通过公开配置隔离；未使用的链路不能偷偷改写原件或产生不可见任务 |
| 从原文抽取知识条目 | 未来优先验证 MemReader 单独调用 | 出现真实派生任务后；输入原文快照，输出另存，不接管基座 |
| MemOS 调度、图存储与生命周期管理 | 首期不引入第二套管理运行时 | 只有前面的单任务方式不够，而且净维护收益可证明时再考虑 |
| 各 agent 的调用时机、上下文预算、产品任务与评测 | 保留现有接入面和度量层 | 不随新后端迁移丢失；后端细节集中在必要适配处 |

**当前有依据的两个入口**：

- OpenViking 的 `add_resource(processing_mode="vectors_only")` 跳过后处理语义摘要，只向量化当前资源。它仍先运行解析，也保留已有语义产物，因此不保证原样入库或旧摘要新鲜；首期用新隔离命名空间验证，不能把旧摘要当当前内容。它是资源处理模式，不是全局“关闭所有 LLM”的开关。[官方资源 API](https://docs.openviking.ai/en/api/02-resources)
- 当前配置文档提供 `memory.extraction_enabled=false`（关闭 session commit 时长期记忆抽取）与 `retrieval.enable_intent=false`（关闭会话查询规划）。两者控制不同阶段；旧 `auto_generate_l0/l1` 已弃用、无运行效果。必须在选定版本实测开关和调用行为，不能仅凭配置文件加载成功认定隔离成功。[官方配置](https://docs.openviking.ai/en/configuration/01-server)
- MemOS 文档公开 `MemReaderFactory` 创建 reader，并用 `get_memory()` 返回 Memory Items，再由调用方保存。这是一个值得验证的抽取接缝；`fine` 模式产生提炼结果，应只放派生区，不能照搬示例中“替换原始快照”的流程。独立接口不证明实际依赖很轻，安装/import/调用仍需测量。[官方 MemReader 文档](https://memos-docs.openmem.net/open_source/modules/mem_reader/)

MemOS 的 scheduler 可以配置为不初始化，但完整 MOS 仍有自己的 reader、LLM、用户与存储组织，不能据此视为纯抽取函数。Python 可选依赖组和 Node/TS 本地插件也不是同一种模块粒度，不能混用它们的能力声明。[MOSCore 源码](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_os/core.py)

### 将来第一次接 MemReader 的形状

```text
选定范围的原文快照 + 输入引用/版本
                    ↓
           隔离任务调用 MemReader
                    ↓
       抽取结果 + 输入引用/版本 + 任务状态
                    ↓
           通过公开操作写入派生区
```

只有出现真实任务时才做这段实现。该任务能读指定输入，不能覆盖原件；它失败不影响原文保存与读取。上层工作结果归你们的产品契约，框架自己的 item/schema 在接入处转换，不扩散到各 agent。暂时不建立双向同步、第二份原文权威、两个相互争抢的调度器，也不维护重复权限表。

### 分离是否成功：停用、升级、恢复三项验证

- **停用**抽取模块后，原文保存、范围读取、检索仍成立；下游模块不是核心读写的隐含依赖。
- **升级**选定后端后，原有接入契约验收通过；不需要修改上游核心、人工修表或逐个改 agent。
- **恢复**时，只靠保存的数据、配置与公开入口重建干净环境，原文一致，权限和关键接入行为可复现。

MVP 先固定具体版本、保存启用配置，补上述外部验收。将来每增加一项能力都记录输入、输出、允许写入范围、处理状态和停用后行为，避免“按需加入”逐渐变成默认启动两套系统。

## 11. 直接复用稳定版本源码：可行的候选路线

2026-10-10：owner 提出 AI 已降低编码成本，可以先讨论架构与边界，再取两个产品稳定版本的部分代码组成自己的产品。认可其技术可行性；本节修正“源码复用只适合小算法”的过窄建议。仍是方案评估，未提取代码、未选择新版本，也未改变旧引擎冻结状态。

### 收益与责任

AI 能加速追踪依赖、改造接口、裁剪初始化与迁移测试。愿意接手一个小范围 fork 时，这条路线可以同时获得已有实现经验、较小部署体积和产品自主性。裁剪后的数据正确性、依赖更新与恢复责任由我们承担；固定上游版本有助于重现，不能证明被拆出的模块已经独立稳定。

选择单位应是**一项能力及其必需的支撑代码与测试**。存储能力可能由文件操作、权限、锁、元数据、后台索引任务与恢复流程共同保证。删除时应先判断某部分只支持可选功能，还是在保障保留能力的数据正确性。

### 当前源码提供的边界线索

- OpenViking 当前 main 的 VikingFS 组合访问、基础操作、同步、语义、快照和向量 mixin；构造接收底层文件客户端、ACL、向量访问等，并使用请求身份上下文与后台任务集合。这里有可裁剪方向，但尚无“复制文件系统目录即可独立使用”的证据。[VikingFS 源码](https://github.com/volcengine/OpenViking/blob/main/openviking/storage/viking_fs/__init__.py)
- MemOS 当前 main 的 SimpleStructMemReader 构造会创建 LLM、embedding 与 chunker，输出采用自身 MemoryItem schema；graph 可以后接。将其作为原文快照到派生条目的处理器值得验证，但仍需要带上必需依赖或显式替换这些接口。[MemReader 源码](https://github.com/MemTensor/MemOS/blob/main/src/memos/mem_reader/simple_struct.py)

这些是 main 的源码观察；选定 tag 后必须重新核对，不能据此宣称已安装的 OpenViking 0.4.23 满足要求。抽取器可以先独立试验；记忆基座的优先级仍由 S1–S3 决定，不能为了易拆而提前建设尚无需求的派生层。

### 建议的三天提取实验

1. **固定基线**：为一项真实需求选定上游 tag、commit 与依赖版本；保留源码来源、许可、相关测试和未经裁剪的参考环境。先跑通上游实现的目标路径。
2. **逐步裁剪**：保留该路径所需代码，每次移除一项能力都重跑相应行为验收。自己的接入面只暴露必要操作；原文和派生产物、引用与版本、允许写入范围、失败状态提前写清。
3. **验证净收益**：在干净环境独立部署，比较依赖、进程、启动流程、模型调用与运维步骤。原文往返、只读来源更新、权限、停机错误、写入中断与恢复必须有证据；复用已有接入及评测资产。

实验期限用来判断可拆性，不代表三天即可交付生产基座。若目标能力仍要求保留近乎完整框架，或必须重写大量存储/权限/后台任务才能正确工作，则该模块没有达到裁剪目的，可转为公开接口接入。尚未证明故障恢复的版本继续留在实验区。

### 维护与许可

保留上游来源与本地改动记录，让后续能够判断某次上游修复是否涉及保留能力。升级按实际修复需要选择，并验证数据格式迁移与恢复；不要求每次上游发布都合并。
