## 1. 问题陈述（架构语言）

**要建的是一台"个人记忆的持久层"**：一个人（单用户）的全部跨会话知识，被他**多个不同的 agent 应用**（今天有 3–4 个：
opencode、一个自建的 DeepTutor 类应用、一个移动端 app、未来的若干）**共同读写**；agent 会换、会升级、会新增。

三条硬性语义：

| # | 语义 | 含义 |
|---|---|---|
| **S1** | **单一真相** | 记忆不隶属于任何单个 agent。换一个 agent 接入，读到同一份，**无需迁移、无需重新培养** |
| **S2** | **两类内容同源** | ① **映射类**：真实文件的映射（项目开发日志 / 关键决策 / 项目概览）；② **虚拟类**：**没有磁盘原件**的条目（移动端 app 总结的文章/视频）。两类都是"真相"，住在同一个寻址空间里 |
| **S3** | **不许被改写** | 写入的内容（无论哪一类）**不得被任何 LLM 二次改写**；派生的摘要/结论**另存**，不覆盖原件 |

长期目标（**现在明确不做**）：在这层之上做"学习"——从记忆里沉淀事实/偏好/结论、生成简报与画像、维护 agent 自己的规则。
即：**先做存储与检索这一层，之后的"调度与巩固"算另一层。**

### 1.1 两个具体场景（提问者原话 + 具体化）

**场景 1 · 碎片知识入库。** 提问者做了一个**移动端 AI 小应用**：他看完视频/文章，app 帮他生成一篇总结，他想把这些总结**存进自己的知识库**。
→ 一处修正：手机**只是前端**；后端不在这台手机上，**最终决定直接跑在他的一台家用 PC 上**。

**场景 2 · 跨项目信息复用。** 他写校招简历时，要用到**另一个项目（本仓库）**的开发信息——做过什么、指标是多少、当时的技术决策是什么。
→ **今天已有活的实例**：只读语料注册表已经把 3 个 repo 收进来，而可写知识库里**又手写了一套** `projects/<slug>/*.md` 摘要 →
**同一项目存在两份表示，必然漂移**。这就是他说的"信息同步问题"。

### 1.2 愿景（原话，未加工）

> "一个个人的知识库，不让信息局限于不同应用、不同机器，我的 personal agent 都要可访问；
> 不只做一个静态、检索的知识库，我希望这个知识库可以后续帮我整理个人的**知识与认知体系**、**总结明白我的个人偏好**；
> 接入它，可以让我**使用一个新 agent 时，这个 agent 不需要我重新培养**。"

### 1.3 场景 → 约束的映射（**为什么抽象需求不够用**）

| 场景／愿景里的那句话 | 它逼出的约束 |
|---|---|
| 手机 app 生成的总结 | **条目没有磁盘原件**（虚拟类），而且这是**最高频的写入源** |
| 项目开发信息 | 真相在**各自 repo 的文件里**（映射类），且必须**只读**——否则必然与 repo 漂移 |
| "今天看的文章和视频" | 需要**按时间 + 来源类型圈定范围**（提问者已决定：**用路径表达，不用元数据字段**） |
| "新 agent 不需要重新培养" | **记忆不隶属任何 agent**；且**新 agent 一接入就要能读到**——"加载时机"是设计问题 |
| "整理认知体系、总结偏好" | 属**需求 2（明确推后）**；但它给需求 1 提了一个要求：**不能丢掉证据基线**，否则以后无从沉淀 |
| "不局限于不同应用、不同机器" | 多 agent 应用 + 多设备读同一份 → **单一权威点 + 明确的降级行为** |

### 1.4 几个典型查询（便于你具体想象）

1. **"给我今天看的文章和视频做个简报"** —— 注意它**跨两层**：**"筛出今天看的"是需求 1，"总结成简报"是需求 2**。
2. **"我在 X 项目上做过什么、当时为什么这么决策"** —— 跨项目的**映射类**检索。
3. **"一个新装的 agent 第一次接入时，应该已经知道什么"** —— 这是"S1 单一真相"的验收形态。

## 2. 硬约束与已知边界（forces）

| 维度 | 事实 |
|---|---|
| 使用者 | **单一用户**（本人 + 他的 agent 们）。**无多租户、无并发多方写者** |
| 数据量 | 现在 **约 40 条自写条目 + 约 220 条只读语料**；预期增长到**千级**，不是百万级 |
| 读取模式 | 少量/天的人问 + agent 检索；**延迟不敏感**（秒级可接受） |
| 写入模式 | 碎片化、**追加为主**、改写（"取代旧条目"）少 |
| 权威点部署 | **一台家用 PC**（基本常开，夜里关机）。**不在云上**（用户明确要求），手机只是前端 |
| 离线 | **不要求**（云端 LLM 本身要联网） |
| 可用性 | 可接受短暂不可用，**但不可用必须显式报错**，绝不能静默返回"没有记忆" |
| 技术底座 | 已有可运行实现：Markdown 为真相源 + git + 派生向量索引 + 单 daemon + MCP 工具面（约 647 个单测、若干评测） |
| 团队 | **提问者不是后端架构师，自述开发经验不多**；开发由 AI agent 执行。**这是本项目的真实约束**，请据此判断"该自持什么、该买什么" |
| 已排除 | 多租户/企业级记忆系统；公网暴露（只走私有 overlay 网络）；把全部基础设施自研到底 |

## 3. 需求分层（必须 / 想要 / 明确不做）

| 层 | 内容 |
|---|---|
| **必须** | 同一份记忆被 N 个 agent 读到；跨设备可达（本机为权威点）；**两类内容都可寻址、可按范围筛（时间/类型/主题）**；**原样保存不被改写**；**范围级读/写权限**（哪些子树 agent 只读、哪些可写）；**版本与备份可恢复**；不可用时显式报错 |
| **想要** | 人可读可带走的形态；迁移/导出；异步后台处理（索引、摘要）**且失败可见**；多入口一致的新鲜度 |
| **明确不做** | 学习/沉淀/画像/简报（需求 2）；多租户；离线；公网服务；实时协作 |

## 5. 真正的待决问题（**这就是我们想请你答的**）

按重要性排序，请尽量给出**结论 + 理由**，而不是"取决于"：

1. **分层与边界怎么划。** 我们目前的想法是四层：
   `存储内核（文件/对象 + 索引）` → `记忆语义（什么是一条记忆、如何取代、范围与权限）` → `上下文装配（把哪些记忆放进 LLM 上下文、预算多少）` → `接入面（各 agent 的 skill/工具）`。
   **这个四层划分对吗？边界画在哪一层最省事？有没有更合适的切法？**

2. **build vs buy 应该发生在哪一层。** 我们的假设是：**存储内核可以买（或直接用一个现成服务），记忆语义必须自持**。
   请判断这个假设。**如果"必须自持的那层"其实很薄，那是不是根本不值得引入外部系统？** 反之如果很厚，买哪一层最划算？

3. **可替换性 vs 用足能力。** 我们已经识别出一个此消彼长：要"内核可替换"，就只能依赖通用标准（POSIX 文件 / Markdown / git / MCP 协议），放弃具体产品的高级能力（分层摘要、私有导出格式、私有查询语义）。
   **对一个单用户、千级数据、一个人+AI 开发的系统，"可替换"值不值得这个代价？** 我们担心自己在为一个不该省的成本省钱。

4. **S2 的两类内容该用同一种存储机制吗？** 尤其"虚拟类没有磁盘原件"这一点：把它也落成文件（人为物化），还是允许"无原件对象"存在于权威存储里？
   **两者在备份/恢复/迁移/审计上的差别是什么？有没有第三种做法？**

5. **这属于哪个已知问题类？请点名参考架构。** 我们自己能想到的相邻概念：personal data store / PIM、local-first software、
   server-authoritative vs local-first sync、content-addressed storage + derived index、"文件系统 + 操作系统"式的分层（上下文窗口当内存、持久存储当磁盘、调度当 OS）。
   **请告诉我们真正贴切的那个，以及值得照抄的先例。**

6. **MVP 砍到什么程度。** 目标只是"先跑起来 + 留对接口"。**请给一个你认为能在一周内跑通、且接口不会挡路的范围。**

7. **YAGNI 检查。** 有没有可能我们正在解决一个**不存在的问题**？（例如：千级数据的单用户系统，是否只需要"一个目录 + 全文检索 + 备份"就够，其余全是过度设计？）

**实测现状**：我们已在一个隔离环境里装好并跑通了其中一个候选产品的**命令面**（约 976 MB、171 个依赖、装了 20 分钟、不需要 Docker），
确认了它有完整的类文件操作（`ls/tree/mkdir/cp/mv/stat`）、**一等权限命令**（按子树授予读/写）、git 式版本（`snapshot commit/log/branch/diff/restore`）、
导出/导入与重建索引；也确认了它的"虚拟条目"通道是实验性的、且它默认会往你的目录里塞 LLM 生成的摘要文件。
**服务端尚未成功启动**（卡在两个环境坑，已定位）。**所以端到端一次都还没跑通。**

**我们的自评（可能是错的，请纠正）**：

- 真正的瓶颈**不是架构推理，而是"我们不了解候选产品，因此判断不了能不能接、怎么接"**；
- 我（提出方）在讨论过程中**不断新增区分与术语**（DB 为核心→虚拟文件系统、商品化/非商品化→按需求判定、框架/实现/应用、6 条内核契约、文件系统/操作系统分层），
  **术语只增不减**，复杂度是被我自己推上去的；讨论的边际收益已经为负；
- 于是我们**停下来求助**，而不是继续讨论。

## 附录 A：评估过的 4 个可买件（只作"哪些能力可以买"的参考，**不要求你评测它们**）

| 件 | 一句话定位 | 对"可买性"的关键属性 |

| **OpenViking**（火山引擎，AGPL） | "一个给 agent 用的虚拟文件系统" | **权威数据在 `localfs` 后端下就是真磁盘文件** → 有"标准落点"；类文件操作 + 子树 ACL + git 式版本 + 导出/重建 |

| **Hindsight**（MIT） | "从交互中学习的会话记忆" | 存储为 Postgres；**有零 LLM 的写入模式与原文取回**；但"学习层"默认全开、成本结构危险 |
| **OpenWiki Brains**（LangChain，MIT） | "自动生成并维护 wiki 的 CLI" | 纯 Markdown 落盘、索引可无限重建；但**原文在记忆接口上不可达**、个人脑没有检索路径、定时器仅 macOS |
