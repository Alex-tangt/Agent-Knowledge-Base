# 0015 Post-MVP 形状：双平面（私有本地 + 企业云）+ 单写者边界

Status: accepted（**D1 的"两平面"主轴已被 ADR-0025 取代**：所有权轴（个人/共享）与部署轴（本地/托管）分离；"企业云"降为共享模式的托管形态。见 `docs/adr/0025`。）

MVP（epic #7）收官后项目进入 Post-MVP。本条记录 #20 起步阶段**已实质拍板**的一簇方向，作为后续设计期 ADR 的地基；隔离策略 / 权限强制点 / 租户粒度等未决项留待 #25 spike 后另立 ADR。

## 决策

**D1 两平面模型。** 记忆分两个平面：

- **私有（本地）**：个人记忆（`classification=private`）；Markdown + git 是系统记录，向量索引是**派生**（ADR-0006 保留）；权限边界 = 本机。
- **企业（云）**：团队 / 组织共享知识（`internal`/`public`）；**云 DB 本身是系统记录**。

单一网关按 `classification`/`residency` 路由读写、统一召回。

**D2 单写者只对本地平面成立。** 企业平面为多写者，委托 DB 的 ACID；不再沿用"单写者 + 路径级单文件 commit"。

**D3 目的地 a → c，且 a 是 c 的前置。** 先做可独立发布的能力包（a），再做多租户企业云（c）。

**D4 模块3 范围收窄。** agent-loop 只做「私有/云 seam 上的 agentic 检索」（在驻留缝上路由 / 规划 / 裁决）；**通用可部署 agent demo（前端 + docker）后延**。

## 理由

差异化在**数据分级驻留 + 统一召回 + 治理**，不在"统一召回"本身（很常见）。企业云若照搬 Markdown + git 派生库，会撞上每租户 git、多写者冲突、审计缺口——故云平面的系统记录必须是 DB。通用 demo 与项目目标关系弱，只增加技术栈广度、不增深度。

Considered options:
- A 双平面 + a→c（采用）——守住本地隐私、把企业侧做成真 DB；代价是架构面变宽。
- B 单平面（全本地 / 全云）（弃）——要么丢企业叙事，要么丢隐私卖点。
- C 先做通用 agent demo（后延）——commodity，稀释叙事、分走治理精力。

## Consequences

- `legal_web` 不再是被优化对象（降为适配层 / 回归锚点）；检索优化对象 = **记忆检索**（#21）。
- 单写者锁（`locks.py` / 常驻 daemon）只覆盖本地平面；企业平面需另设并发模型。
- **真相源契约分裂**：ADR-0006 的适用范围收窄到私有平面——该修订留待 P1 设计期另行记录，**本 ADR 不代替它**。
- 企业侧未选型 → 隔离策略 / 权限强制点 / 租户粒度由 **#25** spike 驱动，另立 ADR。
